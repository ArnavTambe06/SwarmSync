# SwarmSync

SwarmSync is a local proof-of-concept for coordinating three warehouse AMRs. It compares a centralized stop-and-wait baseline with local reservation decisions, displays routes and fleet status, and measures task completion on a shared deterministic workload.

This is a simulation, not robot firmware. MQTT can relay robot state through a local Mosquitto broker when launched with Docker. The current coordination algorithm runs inside the simulator process; MQTT is a telemetry relay here, not yet a transport between independently running robot processes. Browser updates use Server-Sent Events. A production multi-process deployment would need independent robot agents, bidirectional peer messaging, and a broker failover or radio mesh.

## Run locally

Requirements: Python 3.11 or newer. The simulator and dashboard use only the Python standard library.

1. Open a terminal in the project directory.
2. Start the server:

   ```powershell
   python -m swarm.server
   ```

3. Open [http://127.0.0.1:8000](http://127.0.0.1:8000).
4. Select `SwarmSync` or `Stop-and-wait`, then use `Run`, `Step`, and `Reset` to operate the simulation.
5. Select `Compare runs` to run the same task set in both modes. The displayed completion tick counts, collision counts, and time change are generated by the simulator; the 20% target is not assumed to be met.
6. Click any open grid tile to add or remove a temporary aisle blockage. Fixed rack tiles cannot be changed. Watch the coordination feed for route recalculation, yielding, task re-claim, or staging events.

Stop the server with `Ctrl+C`.

## Run with local MQTT

Requirements: Docker Desktop with Compose.

```powershell
docker compose up --build
```

Open [http://localhost:8000](http://localhost:8000). Mosquitto listens locally on port `1883`; while the simulation runs, robot state is published to `swarmsync/robots/{robotId}/state`. Stop the containers with `Ctrl+C`, then run `docker compose down`.

The MQTT broker relays messages and makes no movement decisions. If the local broker or network fails, the simulation's in-process coordination continues, but separately deployed robots would lose this transport. Anonymous broker access is configured for a local demo only.

## File-by-file

| File | Purpose |
|---|---|
| `swarm/engine.py` | Warehouse grid, A* path search, robot/task state, task claiming, baseline movement, decentralized reservation/yield rules, re-routing, staging fallback, and comparison measurements. |
| `swarm/server.py` | Python HTTP API, live event stream, simulation clock, control endpoints, and optional MQTT telemetry relay. |
| `web/index.html` | Dashboard structure, controls, metrics, fleet/task panels, event feed, and comparison report. |
| `web/styles.css` | Responsive warehouse operations interface and grid/robot styles. |
| `web/app.js` | API calls, live updates, grid rendering, blockage interactions, and comparison report rendering. |
| `Dockerfile` | Container image for the Python dashboard and simulator. |
| `docker-compose.yml` | Local dashboard and Mosquitto services. |
| `mosquitto.conf` | Demo-only local broker listener configuration. |
| `requirements.txt` | Optional Paho MQTT client used by Docker mode. Local Python mode needs no packages. |

## API

- `GET /api/state` returns the current fleet and simulation snapshot.
- `GET /api/events` streams snapshots to the browser using Server-Sent Events.
- `GET /api/compare` runs both modes against the same tasks and returns measured ticks and collisions.
- `POST /api/control` accepts `{"action":"run"}`, `pause`, `step`, `reset`, or `{"action":"mode","mode":"swarm"}` / `baseline`.
- `POST /api/blockage` accepts `{"x":7,"y":5,"blocked":true}`.

## What the prototype demonstrates

- Every robot computes routes with A* against the preloaded warehouse map.
- Idle robots claim queued work using nearest-robot distance and robot ID as a stable tiebreak.
- In SwarmSync mode, robots reserve their next cell locally. A conflicting robot yields; wait aging helps a long-waiting robot move up in the next priority round.
- Robots holding cargo try an alternate route first. If none exists, they route to the staging point and enqueue a follow-up delivery task. Physical robot-to-robot cargo transfer is not modeled.
- The comparison uses the same fixed task set and static map in both modes. Results are limited to this simulated workload and are not evidence about physical warehouse performance.

## Current limitations

- The simulator is a single process with simplified grid motion and ideal localization; it does not model robot dimensions, sensor noise, radio range, or real-time edge hardware.
- MQTT publishes state for the dashboard/demo but does not yet connect separate robot processes or deliver reservation requests into the movement algorithm. The local broker is still a transport dependency for that future deployment.
- Live dashboard updates use Server-Sent Events rather than WebSocket. The API and UI are intentionally small so the algorithm can be iterated before adding a Spring Boot service.
- The map and task set are fixed in source. Staging demonstrates queue-based handoff, not physical cargo transfer.
- The report shows the actual measurement even when the 20% target is missed.
